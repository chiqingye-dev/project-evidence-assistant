# 已知限制与 S03 失败案例

2026-11-16 起停止 S03 六条标准满分攻关。保留为开发失败案例，不是 0.5 发布门槛，也不再为它开新试验入口。历史任务、支出和失败稿留在原开发工作区。

十次尝试并非十次完成后都答错：只有第 3、5 次进入源码辅助语义评审，多次在输出格式、计划接纳、冻结或参数校验阶段停止。第 3 次为 5/6；其中错误是把普通 `afterCommit(...)` 方法调用说成传入或注册回调。方法名和调用时机不能证明参数就是回调，必须核对调用表达式和声明。

第 6、8、9、10 次没有保留足以重建拒绝原因的原始参数。已知第 9 次七条 claim 的字段位置不存在，第 10 次是 `section_native.arguments_shape`，但不能倒推实际字段名、标题或超限分支。后来的诊断与 Mock 测试无法恢复那些响应。

模型可能曲解源码；复杂的输出合同又引入了与语义无关的失败机会。此前原文留存不足、单题反复修复、逐次封印流程放大了定位成本。这些是开发过程的问题，不应转化为用户不断输入 Key 或补做检查点的负担。

0.5 减少模型填写的结构并保存脱敏原始响应，校验错误最多反馈两次。程序推导位置可以消除无效字段路径，却不能自动消除“普通调用被说成回调”这样的语义错误。引用存在也不意味着断言被引用支持。

当前仍有这些边界：

- 普通正文支持状态为 `candidate`，语义保持未验证。没有动态运行公开 Java 项目证明真实业务效果。
- 目录、提纲与追问仍使用兼容适配器，简化和纠正目前只覆盖普通正文。
- 固定评测来自已知项目，每题三次；自动词组检查不能判断全部幻觉、否定方向和因果关系。开发者自评不能替代独立评审。
- 两种方法使用同一允许片段池，多数题目已有入口，不能把差异宣传为 Agent 的普遍优势。
- 旧 0.4 正文可读且保留原版本。兼容的 Schema 1 记录可继续作为生成父项，但仍标记需复核；升级不追认语义质量。
- 本地账本按保守单价计算上界，不是供应商余额。缺失可信费用回执会停止后续调用。

0.5 真实固定评测中的两个新例子：Q-sql 的 Agent 第一次输出把按 slug 查询和 `LIMIT 1` 进一步说成“slug 视为唯一键”，但当前读取不含唯一约束；C-parser 的 Agent 第一次输出补充了 Jackson 默认配置及“调用方只需处理一种异常”，这些额外断言不能由本轮片段确认。两份输出的格式和词组检查都通过，保留为自动检查漏检案例，不计为语义满分。

另一个更直接的缺证据例子：G-cache 两种方法的第一次输出都正确保留 TTL 和线程安全未知，却又把传入 `() -> load(slug)` 说成“未命中时回源”。调用点可以证明传入了 lambda，不能单独证明 `cache.read` 何时执行它。该题自动词组检查仍通过，说明缺口词语出现并不等于全文守住证据边界。

面试可以说明：曾发现一个有引用但解释错误的样例，将格式可靠性、源码语义和运行证明分开；随后缩小输出合同、保存可定位响应，并用重复评测与检索基线报告结果。只有亲自读懂并能解释的部分，才应表述为个人掌握。
